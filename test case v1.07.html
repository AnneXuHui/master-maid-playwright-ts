怎么用这份文档
  1. 先完成「P0 全局准备」，把账号、号码、CRM 基础数据填进「测试数据登记表」。
  2. 按编号顺序执行用例。每个用例的 前置准备 写明依赖哪些前序用例、需要哪些数据；产出记录 写明执行后要登记的数据（后面的用例会引用）。
  3. 每个用例下的「多情况」表格是同一功能的不同分支，建议逐行执行并在备注里写实际结果。
  4. 状态、备注、登记表内容保存在本机浏览器中（换浏览器或清缓存会丢失），可用顶部「导出记录」下载一份 JSON 存档 / 交给他人「导入记录」继续。
  5. 文末「待核实问题」是读流程配置时发现的疑似缺陷或需业务确认的行为，对应用例的关注点里也有标注，测试时重点验证。

P0 全局准备（所有用例的前提）

1. 平台与环境

  • Sim 开发工作区已导入 dev/new-lead、dev/new-maid、dev/pre-sales 全部 33 个流程；各 workflow_input 节点的 workflowId 指向本工作区内对应流程（对照 docs/workflow-input-mapping.md）。
  • 环境变量：MASTER_MAID_API_URL 指向 UAT CRM（不能是生产）、MASTER_MAID_API_AUTHORIZATION、AGENT_API_KEY（gemini-2.5-flash 可用）。
  • MATCH_RULE_VERSION 设一个本轮专用的新值（如 MM-001-6 test-20261016），保证匹配结果不会复用以前跑出来的旧结果。
  • WhatsApp 连接：流程中出现的 accountId（684d1816…、3be777a2…、ede2396a…、e3c43050…，触发器 170a7985…）在开发环境都应指向同一个 Bot 号码连接，逐个确认。
  • CRM 时区确认为 UTC+8（scheduler-lead-join-reminder、svc-candidate-lock、create-new-maid 的 claim 过期判断都按 UTC+8 计算）。

2. 测试号码（至少 8 个可收发的 WhatsApp 号码，可一人多号）

角色用途
BOT系统号码，建群、发消息
PRMCRM Contact：custom_prm_id（如 PRM001）、phone、email_id＝Lead 的 lead_owner（对应 User 的邮箱）、full_name 至少两个单词（群名取首字母）
SUPCRM User，角色含 PRM Manager 或 Matching lead，phone 已填
MAT-MM / MAT-PHCRM Nationality：Myanmar → MAT-MM、Filipino → MAT-PH（matcher.phone 已填）；两人都在建档群里，负责提交帮佣资料
E1～E5雇主号码：E1 主链路、E2 竞争同一帮佣 / 暂停恢复、E3 停止、E4 永不入群（提醒）、E5 端到端回归

3. CRM 基础数据

  • 建档群：一个 WhatsApp 群（BOT、MAT-MM、MAT-PH 在内），CRM Chat Activity 有且只有一条 group_type = add_new_maid 的记录，name ＝ 该群 groupId（create-new-maid 只取第一条）。
  • 以下 Doctype 及字段存在且 API 可读写：CRM Lead（custom_process_status、custom_presales_group_id、custom_current_group_id、custom_requirements、custom_group_icons）、CRM Chat Activity（activity、claimed_at、retry_count、matched_ready_at、sent_helper_ids、join_reminder_sent_at、candidate_shortlist、active_candidate_id、pending_confirmation、pending_slot、interview_id）、CRM Maid（availability、summary、full_bio、bio_image、create_by、create_by_phone、reserved_by_group_id、reservation_expires_at、reservation_source）、CRM Maid Match Result、CRM Maid SendTo Group、CRM Processed Message、WhatsApp Submission Claim、CRM Interview Activity。
  • 记下测试开始前 CRM 里 availability = 1 且 bio 完整的帮佣数量（匹配会读整个可用池，已有帮佣也会参与判定，见 TC-02-08）。

4. 定时器策略

  • P1～P5：停用所有 schedule（或把间隔调大），在 Sim 里手动 Run 对应流程，便于一步一步观察。各定时器默认间隔：lead-joining 3 分钟、lead-pending / supervisor-invited / matcher-invited 1 分钟、maid-matched 5 分钟、lead-join-reminder 60 分钟、changed-lead-requirement 50 分钟、job-group-integrity-check 20 分钟。
  • P6：恢复全部定时器，按真实节奏跑一遍。
  • new-maid-trigger 的等待时间在测试环境是 3 × 2 分钟（生产 3 × 10 分钟），P3 用例按 6 分钟计算。
